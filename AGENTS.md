# AGENTS.md — правила работы над MVP

## Прочитать перед изменениями

1. `MVP_SPEC.md` целиком.
2. `docs/STATUS.md`, если уже существует.
3. Текущий код и незакоммиченные изменения.

Этот пакет содержит спецификацию и контрольный пример. Он **не является уже реализованным приложением**. Создай рабочий вертикальный срез, затем расширяй его.

## Приоритет

Работоспособность → корректность → объяснимость → визуальное качество → P1.

Начать с dataset/schema, единой экономики, endpoint evaluate и React-экрана с реальными KPI. После этого добавить граф, расписание, baseline, цепочки и остальные визуализации.

## Инварианты

- Только российские либо явно авторские синтетические операционные данные.
- Нет вызовов внешних LLM, платных карт, runtime-CDN и зарубежных датасетов.
- Локальные библиотеки из спецификации — инструменты, не внешние источники данных.
- Бизнес — перевозчик/3PL; выручка означает плату за транспортную услугу.
- A — базовые условия; B — изменённые условия с прежней политикой; C — адаптация при тех же входах, что B.
- Деньги в целых копейках, расстояния в метрах, время в минутах, вес в кг.
- Финансы рассчитываются только на backend из единого ledger.
- Фиксированная зарплата и владение парком не исчезают от простоя.
- Внешний тариф all-in; собственное топливо на него не начисляется.
- Невыполненная выручка не вычитается дважды.
- Маршрут включает подачу, пустые переходы, обслуживание и возврат на базу.
- Capacity проверяется в каждый момент, а не по сумме тонн за смену.
- Проверять водителя, кузов, окна, смену и остаток пробега до ТО.
- `routing_policy` сохраняет различие возвратного baseline и прямой цепочки.
- После поиска — независимый validator и повторный финансовый расчёт.
- Timeout не равен доказанной невыполнимости.
- Старый API-ответ не становится актуальным после изменения input.
- Никаких fake KPI, декоративных кнопок, случайной «экономии» и ложных AI-labels.

## Процесс

Работать небольшими изменениями. Не переписывать существующий рабочий стек только ради совпадения названий из ТЗ. Существенные отклонения фиксировать в `docs/DECISIONS.md`.

После этапа записать в `docs/STATUS.md`:
- что реально реализовано;
- какие команды запускались и что вернули;
- известные ограничения;
- следующие три конкретные задачи.

Не сообщать о прохождении тестов, если они не запускались. Если источник недоступен, указать это и продолжать на синтетике; не обходить защиту.

## Проверки

Проверочный вход: `data/reference/tiny_economics_fixture.json`.
Ожидаемый результат: `data/reference/tiny_economics_expected.json`.
Описание: `data/reference/README.md`.

Этот пример проверяет арифметику и маршруты, а не точность прогнозов реального рынка.

Команды запуска, lint, pytest, typecheck, frontend build должны появиться в README только после фактической проверки. Финальный demo обязан работать без внешнего интернета после установки пакетов.

## Git и публикация

Не удалять чужие изменения, не выполнять force push, не публиковать репозиторий и не выбирать открытую лицензию без решения владельца. Условия чемпионата по срокам и правам требуют отдельного подтверждения. Не коммитить приватные данные, секреты, node_modules, venv и build-артефакты.
